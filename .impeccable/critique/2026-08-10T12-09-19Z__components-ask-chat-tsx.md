# /ask 问一问体验与能力评审

## 总评

当前界面没有偏离站点的身份轨与连续内容流，也没有出现明显的模板化 AI 视觉问题。问题不在于需要重新设计页面，而在于把已有的检索、文件会话和流式回答能力，转化为用户看得懂、可验证、可恢复的对话契约。

启发式评分：21/40；P0：0；P1：3。认知负荷为中等，主要来自用户必须自行推断检索范围、会话状态和回答证据的时效性。

## 已验证的基础能力

- 检索范围已覆盖全部、每日关注和开源 README；“全部”调用公共检索，单一范围调用 PGroonga 检索 RPC。
- 索引只含公开投影；浏览器不直接访问检索 RPC；公开权限已收回到服务端。
- 请求经 SSE 依次发送来源、文本、完成或错误；客户端支持中断流。
- 会话使用浏览器指纹派生的 HMAC 标识，内容落入权限受限的 JSONL 文件，带 24 小时清理和同会话串行写入。
- Pi 运行配置为最小模式，关闭上下文、扩展、技能、模板和主题，并禁用全部工具。
- 接口为单进程 IP 滑动窗口限流：10 分钟最多 50 次。

## 做得好的地方

1. 身份轨和右侧连续内容流仍然是主框架，没有退化成通用聊天工作台。
2. 输入、范围选择、发送和停止聚合在紧凑的输入区内；键盘 Enter/Shift+Enter 行为清晰。
3. 空状态的三条建议降低了首次提问门槛；来源以标题和段落呈现，方向正确。
4. 浏览器实测范围菜单拥有 radio 语义，窄视口没有横向溢出，控制台没有错误或警告。

## P1：优先解决

### 1. 会话语义与“清空记录”不一致

界面的“清空记录”只清空 React 消息数组；同一浏览器指纹仍会命中同一个服务端 JSONL 上下文。刷新页面时，前端看起来为空，但模型仍可能承接旧上下文。这会同时伤害可控性和隐私预期。

应明确选择一种产品契约：恢复历史并提供“新建会话”，或将当前按钮改名为“清屏”并解释后台上下文仍会保留。基于当前文件会话的目标，优先推荐前者。

### 2. 回答缺少本轮检索证据

回答目前只有“公开资料回答”和来源标题/段落。用户看不到本轮用了哪个范围、命中了多少条、来源类型或发布日期，因此不能快速判断“每日关注”和 README 的权重及新鲜度。

建议在回答顶部加一行轻量元信息，如“本轮检索：每日关注 · 6 条资料”；来源行补充类型和发布日期。保持连续正文，不新增卡片网格。

### 3. 失败无法恢复，草稿也会丢失

提交后输入内容会被清空；服务端仅显示泛化错误，接口限制为 1000 字却没有输入端预检。网络、限流和模型异常后，用户没有重试、回填草稿或倒计时提示。

建议在失败后保留并回填草稿，提供“重试”，输入端显示剩余字数；对于 429，读取 Retry-After 并临时禁用发送、显示可理解的剩余时间。

## P2：随后收束

### 4. 空状态建议与输入框的主次关系

三条建议的视觉存在感略强于输入区，容易让首次用户误解为只能问预设题。保留建议，但降低对比度或增加“示例”提示，使输入框继续是行动的主角。

### 5. 范围下拉略显通用组件化

当前圆角、边框和投影与整体偏扁平的内容流相比稍重。保留上拉式 radio 菜单与可访问语义，但降低投影和装饰感，使其更像排版内的选择器。

## 能力与运行风险

- 当前 50/10 分钟限流只存在单个 Node 进程内；多实例或冷启动环境无法形成全局限额。
- 尚未进行真实的“索引命中 -> Kimi 流式回答 -> 来源渲染 -> 中断”端到端验证，避免了实际模型调用与会话文件写入；现有验证覆盖了接口参数、检索索引单测、客户端 DOM 及错误边界。
- 仍缺少 SSE 事件顺序、客户端流解析、会话过期/权限、清空与新会话、429 UI 的针对性测试。
- 切换检索范围不持久化，刷新回到“全部”；这可以是刻意的轻量选择，但需要与会话契约一起确认。

## 建议的决策顺序

先确定会话可见历史与“新建会话”的产品语义；随后补齐回答元信息与错误恢复；最后微调空状态与范围菜单的视觉权重。这样能够在不加重页面、不把它做成资料库的前提下，让问答真正可信且可持续使用。
